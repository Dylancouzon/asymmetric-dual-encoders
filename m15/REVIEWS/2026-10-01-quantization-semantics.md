# Qdrant 1.19.1 quantization semantics for the E16 pilot (2026-10-01)

This note checks the **tagged Qdrant v1.19.1 source**, not current documentation alone. It addresses the pilot observation (supplied by the owner) that at `ef=64` on one FiQA binary collection, binary search with rescoring and oversampling 1 has lower exact-neighbor recovery than `quantization.ignore=true` by 11.67, 5.10, and 2.29 percentage points for Zero, Nano, and Stella. The result persists at `ef=16` and 256, and oversampling 4 helps. I did not inspect or rerun E16 results.

## What the flags actually do

1. [`is_quantized_search` and `get_oversampled_top`](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/index/vector_index_search_common.rs#L15-L45) make `ignore=true` select unquantized scoring on a quantized collection. With quantized search active, oversampling multiplies the requested top count; `rescore` itself does **not** enter that candidate-count calculation. [HNSW's normal path](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/index/hnsw_index/hnsw/read_view/search.rs#L43-L174) uses that count for graph search and selects the quantized or full-precision scorer. Thus `ignore` is a strong same-collection comparison of quantized versus original-vector **search scoring** on the same stored document set and graph.
2. In the normal HNSW path, [`postprocess_search_result`](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/index/vector_index_search_common.rs#L48-L91) rescoring computes original-vector scores for the returned points, sorts them, and truncates to the requested top count. Within **one segment** at oversampling 1, toggling `rescore` therefore should not change that segment's returned point-ID set; it can change order. At oversampling greater than 1, rescoring can choose a different top-10 subset of the larger segment candidate set.
3. A collection can have **multiple segments**. [The collection searcher](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/collection/src/collection_manager/segments_searcher.rs#L123-L135) merges segment results into a global top-k, and [segment sampling/rerun logic](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/collection/src/collection_manager/segments_searcher.rs#L238-L306) can affect what reaches that merge. Original-vector rescoring can therefore change the **global** top-10 ID set at oversampling 1, even if each segment's candidate set is unchanged. The observed no-rescore→rescore1 set change does not by itself prove a different graph traversal or expanded candidate budget. Inspect segment count and the collection's per-segment results before ascribing that set change to a particular mechanism.
4. There is an [inline-vectors HNSW branch](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/index/hnsw_index/hnsw/read_view/search.rs#L89-L143) when the graph stores inline quantized links: it uses quantized link scores and original-vector base scores within search, and does not use the ordinary postprocess-rescore path. Check whether the pilot's index has inline vectors before applying the one-segment expectation in item 2. In any case, call E16 an **option ablation**, not a clean decomposition into a fixed candidate pool and final reranking.

## One-bit query encoding and changing precision

- [The tagged conversion](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/vector_storage/quantized/quantized_vectors.rs#L148-L180) maps `query_encoding: null` (and explicit `default` or `binary`) to `SameAsStorage`. [The binary encoder](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/quantization/src/encoded_vectors_binary.rs#L737-L753) then encodes the query with the document storage encoding. With default [one-bit document encoding](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/vector_storage/quantized/quantized_vectors.rs#L148-L161), the query is sign-coded one bit per dimension. An explicit `scalar8bits` setting preserves graded query magnitudes with 8-bit query encoding against the binary stored vectors. This is a **collection quantization setting**, not `SearchParams.quantization` at request time.
- [One-bit stored document codes](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/quantization/src/encoded_vectors_binary.rs#L536-L565) depend on each dimension's sign and do not use the query-encoding mode. [Binary internal point-to-point scoring](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/quantization/src/encoded_vectors_binary.rs#L949-L969) also compares stored codes without query encoding. [Graph build](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/index/hnsw_index/hnsw/build.rs#L338-L353) prefers an internal quantized scorer when quantized storage exists. **Inference from these code paths:** changing only `query_encoding` from default to `scalar8bits` should not mathematically change the one-bit document codes or binary internal link scores. It can change query-to-document scores at search time.
- [Quantization configuration mismatch](https://github.com/qdrant/qdrant/blob/v1.19.1/lib/segment/src/types.rs#L1125-L1155) requires a quantization rebuild to apply. The mode is persisted with the encoded-vector metadata, and 8-bit query mode may also cause statistics to be built for the quantized storage. A collection update is therefore **not** a pure request-time knob. Do not claim a same physical graph after changing `query_encoding` unless the graph identity/topology is independently checked. A separate collection comparison would mix query precision with possible rebuild or segment-layout differences.

## Consequence for the next analysis

The existing E16 `ignore` contrast is valuable: it holds the binary collection fixed and tests whether quantized search scoring adds a larger recovery loss for Zero. Phrase it as “quantized scoring on the same graph” rather than a proof that quantization alone changes a fixed candidate pool. For rescore off/on, report full collection results as an option effect. If a mechanistic claim is needed, first record segment count, whether inline vectors are enabled, requested top per segment, and whether sampling/reruns occur. An E17 1M replication can use the same protocol and make the scope broader without introducing a new quantizer or retraining.
