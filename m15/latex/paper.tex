\subsection{Abstract}\label{abstract}

Replacing an embedding model can require re-encoding the entire corpus.
We trained two query encoders for an existing index built with Stella, a
400-million-parameter English embedding model. Constella Nano uses a
smaller transformer. Constella Zero produces dense query vectors from a
learned lookup table without running a neural network. An application
can choose among all three encoders for each request while keeping the
same index.

On a binary-quantized index of one million MS MARCO passages, Stella
took a median of 21.3 ms for query encoding and search. Zero took 1.1
ms, a 19× speedup, and retained 85\% of Stella's relevance score. Nano
took 2.5 ms, an 8.6× speedup, and retained 95\%.

In a matched test on the same workload, Zero scored 24.5\% higher than
BM25 on relevance and took 0.45 ms longer at the median. That makes a
lookup table a practical option for traffic where it meets the
application's relevance target. We show how to test that choice on an
existing index, using judged queries to determine where a cheaper
encoder is good enough and timing the full request to see what it saves.

\subsection{1. Introduction}\label{introduction}

Changing the embedding model behind an existing search index can mean
re-encoding the entire corpus. The query encoder runs on every uncached
request, so replacing that part alone could reduce a recurring cost. We
asked how much of that work a cheaper encoder could take over while the
documents and index stayed fixed.

The original query encoder served as the teacher. We ran it on example
queries and used its output vectors to train a cheaper student encoder.
Because the student learned to produce vectors in the same space, it
could search the documents already in the index. Prior work established
this form of distillation {[}3, 5{]}. We asked whether one index could
support several query encoders with different costs, and how much
retrieval quality each could preserve.

We first tested whether the replacement could still rank relevant
documents well. For a separate set of judged queries, we scored every
document to measure the effect of changing the encoder (§2). We then
measured encoding and search together. A replacement can need a wider
search over the same graph, which can consume some of the time saved
during encoding (§5).

We chose ten public English embedding models with the same tokenizer
vocabulary and used the same method to fit a lookup table for each. On
six retrieval benchmarks, the model with the highest score using its
original query encoder produced the lowest-scoring lookup table. We
chose Stella for the case study because its fitted lookup table scored
highest in that comparison.

We trained two query encoders for Stella. Nano is a distilled
transformer, and Zero builds query vectors from a learned lookup table
without running a neural network. Both Constella encoders can search the
same index as Stella (Figure 1).

\subsubsection{Prior work and scope}\label{prior-work-and-scope}

Prior studies established that a distilled query encoder can search
document vectors produced by its teacher {[}3--5{]}. Static token
representations also reduce query encoding cost {[}6{]}. pyNIFE uses
this approach to fit a lookup encoder for an existing teacher index
{[}7{]}. We applied the same fitting procedure across teachers to test
whether stronger original retrievers yield stronger replacements. We
then measured how much of the encoding speedup remained once search was
included.

Prior studies of graph search have examined how differences between
query and document distributions affect approximate retrieval {[}11,
12{]}. Our evaluation covered related English embedding models, with
fully trained replacements evaluated on Stella's index. The exploratory
graph study covered three workloads in Qdrant with a single graph
configuration.

\subsection{2. Which teachers yield the strongest
replacements?}\label{which-teachers-yield-the-strongest-replacements}

For an existing index, the original embedding model is already the
teacher. We compared teachers to see whether their retrieval scores
could predict how well their replacements would rank documents.

For each of the ten models in Figure 2, we fitted a lookup table and a
projection on top of a frozen transformer. We used ridge regression,
which fits the teacher's query vectors while applying a penalty to
constrain the fitted weights. Both candidates searched the original
model's existing document vectors. The registered comparison covered
lookup tables for those ten models. We also evaluated the transformer
fits in an exploratory analysis {[}1{]}.

We fitted the candidates to the original encoders' vectors for 337,981
queries. To choose the penalty strength, we compared how well each
setting ranked documents on separate judged queries from the CQADupStack
Physics and Programmers forums. We then fixed that setting and evaluated
the candidates on six other datasets using exact cosine search. We gave
each dataset equal weight. Our metric, nDCG@10, rewards placing relevant
documents higher in the top ten results {[}13{]}.

Among the ten registered models, gte-large-en-v1.5 ranked first with its
original encoder and last with its fitted lookup table. Stella produced
the highest-scoring table. Both models used 1,024-dimensional vectors.
The cause of the reversal remains open. We tested 16 more models to see
whether the pattern held beyond the original ten. Across all 26, a
model's original retrieval rank gave little indication of where its
lookup table would rank {[}1{]}.

We also tested whether query-vector similarity could predict retrieval
quality. We measured similarity as the mean cosine similarity between
each table's query vectors and its original encoder's vectors. Both e5
tables matched their original encoders more closely than Stella's table
did, but both scored lower on retrieval {[}1{]}.

The table that ranked first on the development queries also ranked first
on the evaluation datasets. A predictor based on the original encoder's
retrieval score and vector dimension picked a weaker table. In a
follow-up with seven new models with completed table fits, the two
methods picked tables with the same evaluation score {[}1{]}.

For an existing index, use its original model as the teacher. Compare
replacement encoders on separate queries with relevance judgments. In
our registered comparison, fitting a table took four to seven minutes
per model on an A100. That time included encoding the training queries,
except for Stella, whose vectors were already cached {[}1{]}.

\subsubsection{How we fitted the candidate
encoders}\label{how-we-fitted-the-candidate-encoders}

\textbf{Training targets.} For each training query, we ran the original
encoder locally with its usual preprocessing and prompt. We used its
output vector as the target for both candidates. The candidates received
the query text without the original prompt.

\Needspace{9\baselineskip}
\textbf{Lookup table.} Each token had one vector. We initialized it by
running the original encoder on that token alone. All original encoders
shared the BERT WordPiece vocabulary, so the tables covered the same
tokens. The lookup encoder averages these vectors to embed a query. We
fitted the table W by minimizing the following objective.

\[\lVert XW - Y\rVert_F^2 + \lambda\lVert W - A\rVert_F^2\]

Each row of X contains a query's token counts divided by its length, so
XW gives the fitted query vectors. The subscript F denotes the Frobenius
norm. The first term sums squared errors against the teacher's vectors
Y. The second penalizes changes from the initial table A, with
\(\lambda\) controlling the penalty. This helps stabilize vectors for
rare tokens.

\textbf{Transformer projection.} We froze the bge-small backbone. Each
layer produces a 384-dimensional vector for each token. We averaged
those vectors within each layer, excluding padding. A linear projection
can produce 1,024 values from those inputs, but its output can vary
along at most 384 independent directions. Combining the averages from
layers 12, 8, and 4 gave the projection 1,152 inputs and more room to
match the teacher's vectors. In an exploratory test, adding each earlier
layer improved retrieval on both CQADupStack forums {[}1{]}.

We fitted a linear projection and bias by ridge regression to map these
inputs into each teacher's vector space. Both fitted encoders normalized
their output vectors before search {[}1, 15{]}.

\subsection{3. Training Nano and Zero}\label{training-nano-and-zero}

The ridge fits compared two query encoder designs across embedding
models. For Stella's index, we trained Nano and Zero separately and kept
the stored document vectors fixed.

Training a replacement requires vectors from the original encoder for
queries representative of the workload. A hosted endpoint can supply
those targets for the initial transformer fit if it reproduces the
original query vectors. If training includes passages, their targets
come from the document encoder that built the index. The transformer
projection must match the stored vector dimension. Each lookup table row
must match a token ID from the original tokenizer {[}1{]}.

\subsubsection{Training Nano}\label{training-nano}

\textbf{Initialization.} Nano is a 34.5-million-parameter query encoder
built from BAAI's bge-small-en-v1.5 {[}8, 15{]}. With the backbone
frozen, we averaged the token vectors from layers 12, 8, and 4
separately and joined the three averages. We used ridge regression to
fit a linear projection from those values into Stella's
1,024-dimensional space.

\textbf{Training objective.} We then trained the backbone and projection
jointly. For each query or passage, we minimized squared error between
Nano's normalized output and Stella's normalized vector for the same
text. Stella's vectors supplied the training targets without relevance
labels {[}1{]}.

We used three query batches for every document batch. The document
batches exposed Nano to a wider range of text while keeping most updates
focused on queries. The released checkpoint saw about 200 million
training examples, counting repeats {[}1{]}.

\textbf{Development comparison.} We kept generated queries in Nano's
training mix after a registered comparison at five million training
examples per run. The baseline used factoid questions, product queries,
claims, keywords, and titles. Adding seven generated forms and
redistributing the same training budget across all 12 raised mean
nDCG@10 from 0.4903 to 0.5024. MedicalQARetrieval accounted for 82\% of
the gain {[}1{]}.

\subsubsection{Training Zero}\label{training-zero}

\textbf{Initialization.} Zero starts with one vector per token in
Stella's WordPiece vocabulary. We initialized each row by encoding that
token with Stella, using the tokenizer's usual start and end markers.

\textbf{Training objective.} We first trained the table rows and token
weights to reproduce Stella's query vectors. We used both labeled and
unlabeled text for this step. For labeled queries, we also matched
Stella's distribution of scores across the relevant document and 31
other candidates {[}1{]}.

The first stage taught Zero to match Stella's outputs. The second used
relevance labels to train Zero directly on which documents should rank
higher. From a pool of 338,076 labeled query-document pairs, we trained
Zero to score each judged relevant document above alternatives sampled
from a document bank and the training data. To avoid pushing down
potentially relevant results, we excluded known relevant documents and
alternatives that Stella scored nearly as high as the labeled document
or higher {[}1{]}.

\textbf{Development comparison.} At query time, Zero weights each
distinct token's vector by the square root of its count and normalizes
the sum. A token that appears four times gets twice the weight of a
single occurrence. With the int8 rows held fixed, square-root weighting
raised mean development nDCG@10 from 0.6114 to 0.6153. The comparison
was inconclusive on a second checkpoint {[}1{]}.

\subsection{5. Latency and relevance on a shared
index}\label{latency-and-relevance-on-a-shared-index}

Changing the query encoder changes how HNSW navigates the same graph. At
a fixed search breadth, it can miss documents that the new encoder would
rank highly in an exact search. We measured how much search each
replacement needed to stay close to its exact-search score, and what
that cost in latency.

We ran the benchmark on one million MS MARCO passages using Qdrant
1.19.1 {[}16{]} on an Apple M5 Pro. We kept every passage judged
relevant to the 6,980 development queries and sampled the rest, leaving
fewer passages to compete for the top results.

We tested both uncompressed vectors and binary quantization to see
whether cheaper candidate scoring preserved more of the encoding
savings. The binary index used one sign bit per coordinate to find
candidates and rescored them with the original vectors. All three
encoders shared an index within each format. We varied hnsw\_ef, which
controls how broadly HNSW searches the graph. For each encoder and
format, we chose the setting with the lowest median encoding-plus-search
time that retained at least 99\% of that encoder's exact nDCG@10.

\subsubsection{Search breadth across
models}\label{search-breadth-across-models}

The latency savings depended on the workload. On the uncompressed FiQA
index, Zero saved 1.784 ms over Nano at the same 99\% retention
threshold. Nano ranked results better on both FiQA and the MS MARCO
sample {[}1{]}.

Fitted lookup tables often needed a wider search to recover their exact
neighbors. The effect on judged relevance varied by dataset. In an
exploratory comparison of 25 embedding models, each table shared an
index with its original encoder. On FiQA and TREC-COVID, the tables
needed four times the original encoders' hnsw\_ef of 64 at the median to
match their exact top-10 recovery. To match the original encoders'
relative loss in nDCG@10, all 25 tables on FiQA needed a wider search on
average or missed the target at the widest setting. On TREC-COVID, this
applied to 12 of 25 {[}1{]}.

The neighbor recovery gap also changed with index size. After we reduced
FiQA to 25,657 documents and rebuilt the index, the average gap narrowed
from 2.9 to 1.2 percentage points. The smaller sample kept all judged
relevant passages. Qdrant can use full scans on small segments, and we
did not record which segments it scanned {[}1, 16{]}.

\subsection{6. Deployment choices and
costs}\label{deployment-choices-and-costs}

The deployment trade-off depends on the upfront cost of training and how
much traffic a replacement can serve at the required relevance and
latency.

\subsubsection{Training cost}\label{training-cost}

Nano's final optimization took 57.3 hours on an A100, or about \$95 at
the recorded rate. That figure excludes data preparation, earlier runs,
and evaluation. With prepared targets, we estimated that retraining Zero
would take 20 minutes. A new teacher would add an estimated eight to 12
hours to encode the training queries. The companion repository provides
both training implementations {[}1{]}, and the model cards identify the
released checkpoints for the Stella index {[}8{]}.

\subsubsection{Adding a lexical branch}\label{adding-a-lexical-branch}

Pairing Zero with BM25 enables hybrid retrieval without running a neural
network at query time. In the descriptive BEIR-15 evaluation, this
raised Zero's nDCG@10 from 0.4572 to 0.4933. We combined 100 candidates
from each branch using distribution-based score fusion. That gain comes
with a sparse index to maintain and a second search per request. The
registered fusion comparison used convex fusion at a depth of 1,000
candidates {[}2, 17{]}.

\subsubsection{Choosing an encoder for each
request}\label{choosing-an-encoder-for-each-request}

At high query rates, routing requests that Zero can serve at the
required relevance reduces the load on transformer inference. A search
bar could use Zero while users type and Stella on submission, over the
same index. Table 2 measured sequential latency on completed queries.
The search-bar example still requires separate measurements on partial
queries.

We measured encoding and search throughput on Natural Questions using
one Qdrant Edge shard on an eight-vCPU VM. With a warm page cache,
Stella reached 22 queries/s, Nano 605, and Zero 653. At the recorded VM
rate, this implies \$4.91, \$0.18, and \$0.17 per million queries,
respectively. The encoders used search settings that achieved different
relevance scores in the Natural Questions sweep. Nano and Zero reached
similar throughput once search was included {[}20{]}.

Potential savings depend on how often a query benefits from Nano. We
tested this on 12 BEIR-15 datasets. We used relevance judgments to pick
the roughly 15\% of queries per dataset where Nano helped most. The
selector assigned Nano to those queries and Zero to the rest. The
combined score was 0.5163 nDCG@10, close to the 0.5161 from using Nano
for every query. Choosing the better of Nano and Zero for each query
scored 0.5473, compared with 0.5580 for always using Stella {[}18{]}.

Choosing an encoder from query text proved harder. At the same share of
Nano requests, they gained at most 0.005 nDCG@10 over random selection
{[}18{]}.

\subsection{7. How retrieval quality varies across
datasets}\label{how-retrieval-quality-varies-across-datasets}

\subsubsection{Nano against compact dense
retrievers}\label{nano-against-compact-dense-retrievers}

Nano searched Stella's index. We compared it with bge-small, its
original backbone used as a standalone retriever. We also compared it
with LEAF, a compact distilled query encoder that searches its teacher's
Arctic-M index {[}5, 17{]}.

Zero outscored BM25 on the matched MS MARCO benchmark and on the
descriptive BEIR-15 average. The separate registered comparison remained
unresolved. The comparison on datasets without disclosed Stella training
exposure favored BM25. A lexical baseline is therefore still useful when
testing Zero on another workload {[}2, 17, 19{]}.

\subsection{8. Conclusion}\label{conclusion}

A dense index built with a large embedding model can serve some queries
without running a neural network at query time. Zero demonstrated this
on Stella's index. Nano retained more of Stella's retrieval relevance
than Zero and reduced encoding time by running a smaller transformer for
each query. Both used the document vectors already in the index.

The strongest original retriever in our registered comparison produced
the weakest fitted lookup table. Ranking the fitted tables on separate
judged queries gave a better guide to their retrieval quality. On the
uncompressed MS MARCO index, Zero encoded queries about 62 times as fast
as Nano. Once search was included, Zero's median latency was only 6\%
lower. The selected settings retained at least 99\% of each encoder's
own exact nDCG@10. Binary quantization preserved more of the encoding
advantage.

For a search team, the practical question is how much traffic can move
to a cheaper encoder at the relevance the application needs. Exact
retrieval on representative judged queries helps identify request types
where a cheaper encoder meets the relevance target. After tuning search
for each encoder, measuring encoding and search together shows what the
change saves. Teams can use Zero where it meets the target and retain
the original encoder for other requests without re-encoding the corpus.

\subsection{Appendix A. Run settings}\label{appendix-a.-run-settings}

\subsubsection{Model fitting and
training}\label{model-fitting-and-training}

Stella. We used the Stella model revision linked in {[}14{]}. We stored
normalized 1,024-dimensional document vectors in fp16 and used cosine
similarity. Query encoding used fp32, the s2p\_query prompt, and a
maximum length of 512. The fitted students used no query prefix {[}1, 8,
14{]}.

Fitted candidates. We swept \(\lambda\) from \(10^{-4}\) to \(10^{-1}\)
and extended the range by one decade if selection reached an endpoint.
Tokenization included special tokens and truncated at 512 tokens. The
conjugate-gradient residual tolerance was \(10^{-6}\) in fp32 and
\(10^{-8}\) in fp64. We used attention-masked means for the transformer
features and froze bge-small at revision 5c38ec7c. The list of teachers
includes bge-small, so that fitted transformer shares its teacher's
backbone {[}1, 15{]}. An exact rerun requires recovering or
reconstructing the cleaned fitting-query list and verifying it against
the recorded hash {[}1{]}. Across the 26 models in the exploratory
lookup-table comparison, Spearman's rank correlation was +0.09 (95\%
interval −0.39 to +0.52) {[}1{]}.

Full training. Zero ran 16,000 steps of alignment and teacher-score
matching at batch 512, then 2,500 contrastive steps with 32,768 bank
negatives plus supplied negatives. We masked known positives and
candidates whose Stella score exceeded the positive document's score
minus 0.02. Nano used AdamW at batch 32 over three learning-rate cycles
from \(10^{-4}\) to \(10^{-5}\). The released model is the endpoint of
the third cycle. The companion configs pin the losses, sampling,
schedules, and source manifests {[}1{]}.

Nano initialization. We randomly sampled 60,000 queries from Nano's
training pool using seed 21. We fitted the projection on 50,000 and
chose the penalty on the remaining 10,000 by comparing vector error.
With the penalty fixed, we refitted the projection on all 60,000 queries
{[}1{]}.

Nano training data. The pool contained 3,486,034 unique queries,
including 834,462 generated from passages, and 6,070,049 eligible
document passages. Seven of the 12 query forms used generated text. We
screened and monitored training on separate judged queries from BRIGHT,
MedicalQARetrieval, LEDGER, and LegalBench {[}1{]}.

Synthetic training data. We used Qwen3-8B-AWQ revision 4da05a8e at
temperature 0.8 and top-p 0.95 with thinking disabled. Finance and
health prompts used Wikipedia passages. The other generated forms used
HotpotQA passages. The filters checked length, duplication, held-out
overlap, and spans of five or more copied words. We used Stella to
encode the accepted queries {[}1{]}.

\subsubsection{Retrieval and timing
benchmarks}\label{retrieval-and-timing-benchmarks}

BEIR-15 adds FEVER, DBpedia-entity, CQADupStack, MS MARCO, NQ, HotpotQA,
Webis-Touche2020, Quora, and Climate-FEVER to the six-dataset suite. The
descriptive BEIR-15 score weights datasets equally. CQADupStack counts
as one dataset after forum aggregation and includes both forums used for
development.

MS MARCO supplied no training targets, negatives, or generation seeds.
Nano's pretrained backbone had prior exposure. We reconstructed the
million-passage identifier list from the pinned public corpus and
development judgments using seed 20260930. Its SHA-256 hash matched the
recorded value. Binary sweeps tested oversampling of one, two, and four
{[}1, 2, 13{]}.

The encoding benchmark used 100 queries of five to 12 words, warmed
inference, batch size one, and four CPU threads on an Apple M5 Pro
{[}9{]}.

The exploratory VM benchmark used 30-second runs with batch size one and
one, two, four, or eight worker threads. We report the highest
throughput observed for each encoder at the recorded VM rate of \$0.395
per hour. Zero used the highest-scoring setting in the Natural Questions
search sweep, which retained 98.5\% of its own exact nDCG@10. Nano and
Zero saw NQ Open training questions. The benchmark used Natural
Questions test queries {[}20{]}.

With one worker, Zero completed 640 queries/s in the run with a primed
page cache and 42 queries/s in the run that started without priming
{[}20{]}.

Zero footprint. At export, we folded the learned weights into the rows
and stored them as int8 to reduce the table size. The complete 90.1 MiB
package includes the int8 rows and an fp16 reference table. The measured
loader expands the selected table to fp32, and peak process memory was
360 MiB under the encoding protocol {[}8, 9{]}.

\subsubsection{Graph search}\label{graph-search}

The exploratory comparison used FiQA, SCIDOCS, and TREC-COVID. For each
embedding model and workload, we built two indexes with different
insertion orders in Qdrant 1.19.1, using cosine similarity and HNSW with
m=16 and ef\_construct=100 {[}10{]}. We swept hnsw\_ef from 16 to 512
and computed breadth ratios per build against the original encoder at
64.

The exact-search agreement check used 200 queries per encoder with a
threshold of 0.995. The fitted tas-b transformer failed the check on
SCIDOCS, leaving 25 models. A returned document counted toward recovery
if its exact cosine score was at least the exact tenth neighbor's score
minus \(10^{-4}\). The FiQA size control retained judged positives,
sampled to 25,657 documents, and rebuilt both graphs {[}1, 16, 17{]}.
