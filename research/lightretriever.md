## 1. Paper mechanics

### 1.1 Query encoder: the lookup table is NOT the LLM's input embedding matrix

This was the single most important thing to pin down, and the answer is unambiguous. The table rows are produced by **running each vocabulary token through the trained LLM** and caching the result. Reusing the raw input embedding layer is a different setup, which the authors tested as an ablation and which loses 11.2 nDCG@10 on BEIR.

Paper, Figure 3 caption (three stages):

> 1) Training: A shared prompt concatenated with a single query token is passed through a full encoder independently to obtain token-level representations. The full query representation is then computed by averaging the token vectors corresponding to each query token. 2) Caching: Prior to serving, the trained encoder is used to precompute token embeddings for the entire LLM's vocabulary, which are stored in a single embedding lookup matrix. 3) Online Serving: At inference time, query embeddings are efficiently generated by lookup and averaging the cached token embeddings, eliminating the need for deep model inference.

Paper, §2.2 "Caching":

> Query tokens do not deeply interact with each other. Thus, the query token vectors are cacheable. Given a certain vocabulary with size [V], all token vectors are precomputed as in Equation 3 and stored in a lookup Embedding. Typically, caching such a lookup Embedding on 8 H800 with a Llama-8b model consumes less than 20s, which is a one-go and cheap operation.

Paper, §2.2 "Online serving":

> LLM-based encoders are no longer needed during online serving. Instead, only one Embedding layer, with a single weight matrix shaped [V, H], is hosted in RAM. [H] is the dimension of LLM's hidden states, which is also the dimension of dense vectors. The dense query vector is obtained with a simple lookup-then-average operation, which is super efficient with or without GPU acceleration.

The ablation that rules out the raw embedding matrix, paper §4 (A2):

> To confirm that a deep query encoder is still needed during training, we replaced the Transformer-based query encoder with a simple Embedding Bag that reuses only the LLM's embedding layer. This setup significantly degrades performance (-11.2 on BeIR, -17.4 on CMTEB-R), indicating that although deep token interaction could be limited with a durable cost during query inferencing, the full-sized modeling for query side training remains essential to learn effective representations.

### 1.2 Exact table construction procedure

From `src/lightretriever/finetune/nonctx_emb_utils.py`, `construct_embedding_bag()` docstring (this is the authoritative quote for building the table):

> Construct prompted token embedding bags.
> This fuction will construct inputs formated in `[bos] + [prompts] + [vocab_token_id] + [eos]`,
> then we pool the hidden states from eos as the embedding of coresponding vocab_token_id.
> vocab_token_id ranges [0, len(tokenizer)).

Mechanically, per row `i` of the table:

1. Build `input_ids = [bos] + tokenize(instruction_prompt) + [i] + [eos]`. The `bos` is included only if `bos_token_id in tokenizer.encode("", add_special_tokens=True)`. **CORRECTION (2026-08-25): this fires for the shipped Qwen tokenizer too.** The adapter repo's tokenizer bakes a `<|bos|> … <|endoftext|>` post-processor into `add_special_tokens=True` (base Qwen adds nothing), so bos IS required for Qwen tables. Building without it costs −2 (SciFact) to −12 (ArguAna) nDCG@10 — measured in `bench/diag_bos.py`.
2. Forward through the merged LoRA model's base transformer (`hf_model.model`, i.e. `LlamaModel`/`Qwen2Model`, so post-final-norm hidden states). No attention mask is passed, so plain causal attention over a sequence of `len(prompt) + 2` tokens.
3. Take `last_hidden_state[:, -1]`, the hidden state at the `eos` position. That is the row.
4. Rows accumulate into a `float32` tensor of shape `[len(tokenizer), hidden_size]`, then wrapped as `torch.nn.EmbeddingBag.from_pretrained(final_embedding, padding_idx=tokenizer.pad_token_id)`.

Batching is over vocabulary ids, default `batch_size=2000` (the notebook uses 1000). The prompt region is identical across the batch, only position `-2` varies.

**EOS handling.** The `eos` token is appended after every vocabulary token, and its hidden state is the pooled representation. This is standard last-token pooling, consistent with the document side. During training the same shape is used per query token, and a custom 4-D attention mask (`micro_block_width=2`, i.e. each `[token, eos]` pair is one block) lets all query tokens share one prompt forward pass without attending to each other. That mask is a training-time throughput optimization only; the caching path does not use it.

**Weighting and normalization.** No learned weighting. `EmbeddingBag` defaults to `mode='mean'`, so the query vector is the plain unweighted arithmetic mean of the rows for the query's token ids, with repeated tokens counted once per occurrence. Then L2 normalize. From `scripts/asymmetric_dense_infer.ipynb`:

```python
query_embeddings = emb_bag(input=input_ids, offsets=offsets)
query_embeddings = torch.nn.functional.normalize(query_embeddings, p=2, dim=-1)
```

Query tokenization for lookup uses `add_special_tokens=False`, `max_length=512`, `truncation=True`. No bos, no eos, no instruction text at query time. The instruction is already baked into the table.

**The table is instruction-specific.** This is the detail most likely to be missed and it matters a lot for the edge architecture. The `prompt` argument to `construct_embedding_bag` is the task instruction, and `EmbeddingBagMixin` caches `emb_bag_prompt` alongside the table. The eval loop rebuilds the whole table whenever the task instruction changes:

```python
# src/lightretriever/inference/exact_search_torchrpc.py:141-149
emb_bag_prompt = self.query_prompt or dataset[0].get("prompt", None)
...
emb_bag_exists = self.model.emb_bag is not None
emb_bag_need_recompute = self.model.emb_bag_prompt != emb_bag_prompt
if (not emb_bag_exists) or (emb_bag_exists and emb_bag_need_recompute):
```

So reproducing the published BEIR average means building **15 tables**, one per task instruction. A single edge deployment gets one instruction, which is a real quality question the paper does not isolate.

Instruction format (§A.7), following E5-Mistral:

```
Instruct: {instruction}\nQuery: {query}
```

The prompt passed to `construct_embedding_bag` is the whole prefix including the trailing `Query: `. From `scripts/cache_emb_bag.ipynb`:

```python
prompt="Instruct: Given a web search query, retrieve relevant passages that answer the query\nQuery: "
```

### 1.3 Document encoder

- Full merged LoRA model, base transformer output (`hf_model.model`), **last-token (eos) pooling**, then L2 normalize.
- **No document instruction.** §2.1: "In our work, dense retrieval follows the query instructions of Mistral-E5 and does not involve passage instructions." The stated reason is index reuse across tasks. Good news for us: one document index serves every task.
- Max length 512 (`--p_max_len 512` in `eval/README.md`; training also used 512).
- Tokenized with `add_special_tokens=True` (so bos is added for Llama), `padding="longest"`.
- Similarity is cosine (`--score_function cos_sim`), which given both sides are L2-normalized is a plain dot product.

Pooling helper from `scripts/asymmetric_dense_infer.ipynb` handles both padding sides:

```python
def lasttoken_pooling(last_hidden, attention_mask):
    left_padding = (attention_mask[:, -1].sum() == attention_mask.shape[0])
    if left_padding:
        return last_hidden[:, -1]
    sequence_lengths = attention_mask.sum(dim=1)
    return last_hidden[torch.arange(last_hidden.shape[0]), sequence_lengths - 1]
```

### 1.4 Sparse component: runnable from released artifacts, no extra head needed

The sparse side is SPLADE-style but with a completely free query side.

- **Query**: raw token counts. No model at all. `dict(Counter(tokenizer(query, add_special_tokens=False)["input_ids"]))`. §2.3: "The sparse query vector directly maps a token and its corresponding quantity". §2.3 online serving: "No more query encoder for sparse retrieval is needed." Also note §2.1: "The sparse retrieval is incompatible with instructions because it does not involve learnable query encoders."
- **Document**: last-layer hidden states projected to vocabulary space **through the model's own existing LM head**, then `log1p(relu(...))`, then max-pool over sequence length.

```python
aggregated_logits = torch.log1p(torch.relu(torch.amax(lm_out.logits, dim=1)))
```

**No extra head files are required.** The LoRA adapters target only `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` with `modules_to_save: null`, so the LM head is the frozen base model's own head. Everything needed ships in the base model plus the adapter. Confirmed against every `adapter_config.json` in the org.

Scoring is a dot product over the intersection of token ids, so query term frequency times learned document term impact. Hybrid = linear sum of L2-normalized dense and sparse scores (§3.1: "The hybrid similarity scores are linearly summed from normalized dense and sparse scores").

**Exact fusion scheme, verified in the repo** (this is what "normalized" means operationally): `eval/eval_arguments.py:48-53` defines `fuse_weights` with default `[0.7, 0.3]` — "Default to 0.7 for emb (Light Dense), 0.3 for tok (Light Sparse). Optimal performances could be further tuned based on tasks and models." `src/lightretriever/retriever/hybrid_search.py:34` sets `score_fuse_method: str = "linear"` as default, and `src/lightretriever/retriever/score_fuse_utils.py::fuse_scores_linear` implements it: per query, each system's candidate scores are min-max normalized to [0,1] (`(s - min) / (max - min + eps)`), then summed with the weights. Our `core.fuse_linear` replicates this exactly, including the 0.7/0.3 defaults. The weights are the repo's defaults, not tuned on our test sets. Caveat carried to the report: min-max is computed over each system's own top-k candidate list, so "absent from the other list" scores 0 there.

Training used a FLOPs sparsity regularizer (coefficient 0.001, quadratically ramped over the first 4k steps). That is training-only; nothing to configure at inference.

An auxiliary KL loss between the lookup-table query vector and the full-model query vector was also used. Its contribution (Table 10, Llama-3.1-8B): dense 52.0 vs 50.8 without, sparse 49.5 vs 48.7, hybrid 54.4 vs 53.9. The released adapters are the "with KL" ones.

### 1.5 Matryoshka variant and table sizes

MRL is trained by slicing the leading `k` dimensions and applying the same contrastive loss at each `k`. Truncation at inference is slice-then-renormalize (`modeling_hybrid.py:604-621`):

```python
def shrink(self, tensor, dim):
    if not dim: return tensor
    tensor = tensor[..., :dim]
    if self.model_args.normalize:
        tensor = F.normalize(tensor, p=2, dim=-1)
    return tensor
```

**Only `lightretriever-llama3.1-8b-mrl` is trained for truncation.** Slicing any of the other seven adapters is untested and should be expected to degrade sharply.

### 2.2 The one precomputed lookup table

`lightretriever/lightretriever-mistral0.3-7b` ships `web_search_en.emb_bag.pt`, 268,436,740 bytes.

Verified by reading the file header directly: it is a zip-format torch save whose internal storage key is **`msmarco.emb_bag`** and whose dtype is **`BFloat16Storage`**. Size math confirms shape `[32768, 4096]`: 32768 * 4096 * 2 = 268,435,456 bytes plus a 1,284-byte pickle header.

So it is the full-dimension bf16 table for Mistral-7B-v0.3 built with the MS-MARCO / web-search instruction, `"Instruct: Given a web search query, retrieve relevant passages that answer the query\nQuery: "`. **This is the only precomputed table released.** Every other backbone, and every other task instruction, has to be built locally.

### 2.3 Dataset

`lightretriever/lightretriever-finetune-data`, 23.5M rows, ~4.3k downloads. All 23 fine-tuning sets with hard-negative mining and test-set deduplication, following tDRO's preparation. Only needed if we retrain.

### 2.4 Official inference code

`github.com/caskcsg/lightretriever`, Apache 2.0. Three notebooks under `scripts/` are exactly what we need and they are short and clear:

- `cache_emb_bag.ipynb` — load base + adapter, `merge_and_unload()`, `construct_embedding_bag(prompt=...)`, `torch.save(emb_bag.weight, ...)`.
- `asymmetric_dense_infer.ipynb` — load table, lookup+mean+normalize for queries; merged model + last-token pooling + normalize for documents; dot product.
- `asymmetric_sparse_infer.ipynb` — `Counter` for queries; `log1p(relu(amax(logits)))` for documents; sparse dot product.

Plus `finetune_example.sh`, and a distributed MTEB eval harness under `eval/` built on torch RPC. Notebook default model is `lightretriever/lightretriever-qwen2.5-1.5b`, which is a useful signal about what the authors themselves run for demos.

`flash-attn` is an **optional** extra (`[project.optional-dependencies] fused_kernel`), not a core dependency. `attn_implementation` is a plain argument with documented choices `flash_attention_2`, `sdpa`, `eager` (`arguments.py:345`). No `trust_remote_code` anywhere. Core deps: torch >= 2.2.2, transformers >= 4.47.0, peft >= 0.10.0, mteb >= 1.14.15, faiss, plus `numpy <= 1.26.4` pinned because faiss lacks numpy 2 support.

Published eval settings from `eval/README.md`: `--q_max_len 512 --p_max_len 512 --bf16 --score_function cos_sim --pooling_strategy lasttoken --add_prompt --prompt_type e5`, sparse with `--sparse_use_max_aggregation --sparse_use_relu --sparse_use_log_saturation`. Embedding-type flags are mutually exclusive per MTEB run: `--hybrid_use_dense_vector` (symmetric), `--hybrid_use_emb_vector` plus `--noncontextual_query_embedding` (LightRetriever asymmetric dense), `--hybrid_use_token_id_vector` (asymmetric sparse), or the last two together for hybrid.

Category retention, Table 3, Llama-3.1-8B full vs light:

| Task | Datasets | Full | Light | Retention |

| Fact Checking | FEVER, ClimateFEVER, SciFact | 70.8 | 67.6 | 95.5% |
| Duplicate Question Retrieval | CQADupstack, Quora | 69.6 | 65.3 | 93.8% |
| Passage Retrieval / General QA | MSMARCO, NFCorpus, NQ | 50.1 | 47.0 | 93.8% |

Reasoning-heavy and code retrieval degrade much harder. BRIGHT (Table 18): LightRetriever-Llama3.1-8B averages **11.8 vs BM25's 14.5 and E5-Mistral's 17.9**. It loses to BM25. CoIR (Table 17): 48.8 vs E5-Mistral 55.2, though still well above BM25's 29.8. §A.1 concedes the point: "Tasks that require complex query understanding, such as reasoning-intensive retrieval, are not suitable for our work."

Ablations (Table 5, Llama-1b dense baseline 48.7 BEIR / 58.7 CMTEB-R):

| Ablation | BEIR | CMTEB-R |
|---|---|---|
| Ours (train full/full, infer Emb/full) | 48.7 | 58.7 |
| A1: both sides light at inference | 34.9 (-13.8) | 40.1 (-18.6) |
| A2: query trained as Emb Bag over the LLM's embedding layer | 37.5 (-11.2) | 41.3 (-17.4) |

Also noted in §4: a reversed asymmetry (deep query, light document) showed "training instability and degraded performance, likely caused by embedding collapse."

## 4. Feasibility on M5 Pro / 24 GB / MPS

Environment as of this writing: `hw.memsize` = 25,769,803,776 (24 GiB), Mac17,9, macOS 26.4.1, `uv` 0.11.17 present, **no torch installed yet** in any discoverable interpreter. So M3 starts with an env build.

### 4.1 Recommendation

**Primary: `lightretriever/lightretriever-qwen2.5-1.5b`.**

Reasons, in order of weight:

1. Ungated Apache-2.0 base (`Qwen/Qwen2.5-1.5B`). Every Llama base is gated behind manual approval, which is an unbounded wait we should not put on the critical path. Qwen2.5-3B is ungated but carries the non-commercial Qwen Research license, which is a bad choice for anything that may inform a Qdrant deliverable.
2. bf16 weights are ~3.1 GB. Leaves plenty of headroom for the float32 `[151666, 1536]` accumulator (932 MB) during table construction and for a document index.
3. It is the default in all three official notebooks, so it is the best-tested path.
4. Published dense 48.9 / hybrid 52.1 BEIR, which already clears BGE-m3-dense at 47.2. Good enough to make the point.

**Secondary, once the harness works: `lightretriever/lightretriever-mistral0.3-7b`.** Ungated Apache-2.0 base, the best LightRetriever scores in the paper (dense 52.7, hybrid 54.5), and the only repo with a **precomputed table**, so we can validate our own table construction against theirs before trusting it. Its 32K vocabulary also gives by far the smallest edge artifact (268 MB full, 8.4 MB at 128 dims), which makes it the most interesting backbone for the actual edge story. Cost: 14.5 GB bf16 weights on 24 GB is tight but workable if nothing else is resident, and document encoding will be roughly 5x slower than the 1.5B.

**Skip `llama3.1-8b` and `qwen2.5-7b`.** 16 GB and 15.2 GB of bf16 weights plus a 2.1 GB float32 accumulator, on a 24 GB unified-memory machine also running the OS, is not worth the trouble for a few points. If we want the 8B numbers, they are in the table above.

**The MRL story requires `llama3.1-8b-mrl`, which is gated.** If dimension truncation matters to the deliverable (and for edge artifact size it probably does), request Llama access now so it is not blocking later. Truncating the Qwen or Mistral adapters is untrained and should not be reported as an MRL result.

### 4.2 Expected cost of building a table

The work is `len(tokenizer)` forward passes over sequences of `len(prompt_tokens) + 2` tokens, roughly 20 tokens each with a typical BEIR instruction. For Qwen2.5-1.5B that is ~151,666 sequences, about 3.0M tokens of prefill, batched at 1000-2000 vocabulary ids per forward.

At a plausible MPS prefill rate of 2-6k tok/s for a 1.5B in bf16, that lands around **10 to 25 minutes per table**. Worth measuring rather than trusting. The consequence to plan around: **one table per BEIR task instruction**, so a 15-dataset run means 15 tables and possibly several hours of table building alone. Two mitigations: pick a small BEIR subset per the project constraints, or build one table with the MS-MARCO web-search instruction and accept the mismatch, which is closer to the real edge deployment anyway and worth reporting as its own data point.

Document encoding is the other cost and it is the same order as any 1.5B embedding run. Pick small corpora: SciFact (5.2k docs), NFCorpus (3.6k), ArguAna (8.7k), SCIDOCS (25k), TREC-COVID (171k, borderline). Avoid FEVER, HotpotQA, MSMARCO, DBPedia, Quora, CQADupStack at this stage.

### 4.3 Gotchas, ranked

1. **The lookup table is per task instruction, and only one table is released** (Mistral, MS-MARCO instruction, bf16, full 4096 dims). Everything else we build ourselves. Reproducing a published BEIR average means 15 table builds. This is the biggest hidden cost in the whole plan and it is not visible from the paper's framing.
2. **All Llama bases are gated (manual approval).** That silently removes `llama3.2-1b`, `llama3.2-3b`, `llama3.1-8b`, and critically `llama3.1-8b-mrl`, the only MRL model. Request access on day one.
3. **`torch.autocast(device_type=model.device.type)` inside `construct_embedding_bag` is a CUDA assumption.** On MPS, autocast is either unsupported or defaults differently depending on the torch version. Load the merged model in bf16 explicitly and either drop the autocast context or pin `dtype=torch.bfloat16`. This is a one-line patch but it will be the first thing that breaks.
4. **Swap `attn_implementation="flash_attention_2"` for `"sdpa"`** in all three notebooks. flash-attn is an optional extra, not a hard dependency, so nothing else needs to change. There is no `trust_remote_code` anywhere, and no custom modeling code.
5. **Load the tokenizer from the adapter repo, not the base repo.** The adapter repos set `pad_token` deliberately (Llama has none by default), and `EmbeddingBag.from_pretrained(..., padding_idx=tokenizer.pad_token_id)` fails on `None`.
6. **`construct_embedding_bag` allocates the accumulator in float32 on the model's device.** 932 MB for Qwen2.5-1.5B, 2.1 GB for an 8B. Cast to bf16 or fp16 before saving, matching the released file which is bf16.
7. **`numpy <= 1.26.4` is pinned** because faiss lacks numpy 2 support. If we use our own exact-search code instead of faiss, as the project constraints suggest, we can drop faiss and the pin along with it. Anserini also needs a JDK 17 and a downloaded jar, only for sparse retrieval.
8. **Don't compare the paper's dense and hybrid numbers interchangeably.** Table 2, Table 1, and Table 9 all report hybrid for LightRetriever rows. The dense-only column, which is what an edge vector-lookup architecture actually gets, is 2 to 3 points lower. Table 9's 128-dim figure of 49.3 is hybrid; dense-only at 128 dims is unreported.
9. Table 9's index sizes (134.92 GB dense for 8.8M passages) are for 4096-dim fp32-equivalent storage. Irrelevant to our small-subset plan but worth remembering when the report discusses edge index size.
