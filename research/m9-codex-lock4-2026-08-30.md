# Verdict

Finish the in-flight `m9s1`; it is on a coherent incumbent path. **Do not launch Stage B yet.**

The current state has three real blockers:

1. The reordered Stage B violates the binding mandate and its “void later” mechanism is not safely enforced.
2. The challenger bf16 repair does not invalidate old fp16 caches and can return a stale combined cache.
3. `decide()` can publish an eligible incumbent decision before the teacher arms finish, and that decision can remain stale after newer arms appear.

The numerical results look credible. The machinery around them does not currently make them decision-eligible under the active session.

## Findings, highest severity first

### BLOCKER — the Stage B reorder is a protocol breach, not a stronger equivalent

The mandate says teacher arms first and explicitly says order/baselines cannot change after arm 1 starts ([instructions-m9.md](/home/dylan/asymetric-dual-encoders/instructions-m9.md:108)). The reorder happened after Stage A results and after the stella-1.5B arm failed operationally. “No teacher comparison number existed” prevents outcome-driven teacher selection, but it does not satisfy the mandate.

Scientifically, I would call it a defensible operational amendment—not classic p-hacking—but the ledger’s claim that the void rule is “stronger” is rationalisation. Teacher-first prevents invalid downstream experiments; the new rule runs them, inspects them, and promises to discard them later. Those are not equivalent.

Worse, the promise is incomplete:

- `decide()` defaults the teacher to the incumbent whenever both teacher arms are not present ([screen.py](/home/dylan/asymetric-dual-encoders/m9src/screen.py:383)).
- It then writes a normal, eligible `m9_screen_decisions.json` ([screen.py](/home/dylan/asymetric-dual-encoders/m9src/screen.py:414)).
- Nothing marks that artifact provisional or requires all decision arms before M9.2 can consume it.
- A later teacher result does not automatically invalidate an older decision artifact.
- The STOP check reads the decision artifact, not the raw teacher-arm outcomes ([screen.py](/home/dylan/asymetric-dual-encoders/m9src/screen.py:89)).
- The runner deletes and recreates the decision token to support repeated interim decisions ([run_m9_stage.sh](/home/dylan/asymetric-dual-encoders/run_m9_stage.sh:20)).

Therefore, **yes: change 6 creates a path for a decision to stand that should not.** If teacher arms fail, are skipped, or finish without a final `decide()` rerun, the incumbent default can become the de facto teacher selection.

Required fix:

- Dylan explicitly ratifies the reorder.
- Rename interim output to `m9_screen_state.json`; it must be ineligible for M9.2.
- Final `decide()` must require all mandatory arms and carry `complete: true` plus hashes of their artifacts.
- Any newly written arm must mechanically stale the previous decision.
- M9.2 must refuse anything except a complete final decision.

### BLOCKER — bf16 does not invalidate the old fp16 challenger cache

The bf16 compute change and exhaustive finiteness check are good. The cache implementation undermines them.

The cache key includes repo, revision, prompt, role and corpus, but **not compute dtype or `config_kwargs`** ([teacher9.py](/home/dylan/asymetric-dual-encoders/m9src/teacher9.py:121)). Switching fp16 → bf16 therefore addresses the live encoder but can reuse already-hashed fp16 chunks—including the NaN-producing output.

There is a second cache bug: if a bad chunk is re-encoded but `combined.f16` already has the expected byte size, the combined file is not rebuilt ([teacher9.py](/home/dylan/asymetric-dual-encoders/m9src/teacher9.py:158)). The function can return stale combined bytes after successfully repairing a chunk.

The exhaustive check will stop NaNs from reaching training, so it earns its cost. But the arm may simply keep aborting instead of benefiting from bf16.

Before either teacher arm:

- Put compute dtype, effective model config, relevant library version and encoder-code hash in the cache key.
- Hash the combined cache, or always rebuild it whenever any chunk is written.
- Add a challenger-specific bf16-live → fp16-cache numerical gate. The incumbent’s fp16 gate says nothing about challenger vector distributions.

### MAJOR — the session guarantee is not what pass 2 requested

The remaining guarantee is:

> All arms share the same hash over the files currently listed in `GUARDED`, `CODE`, and `DATA`; at checks, those files are clean and current HEAD is pushed on `m9-work`.

It no longer guarantees one commit, and the recorded artifact commit is the session-opening commit rather than necessarily the arm’s actual HEAD.

More importantly, the fingerprint is both overbroad and incomplete:

- Overbroad: every arm depends on `teacher9.py`, so challenger-only changes void the incumbent anchor.
- Incomplete: it omits the binding `instructions-m9.md`, `run_m9_stage.sh`, dev/qrel/vector assets, target-cache contents, and verified runtime settings ([guard9.py](/home/dylan/asymetric-dual-encoders/m9src/guard9.py:35)).
- `eligible()` proves that a token was consumed, not that the current payload is the payload written by that token. An artifact can be edited while retaining its copied registration block and remain eligible ([guard9.py](/home/dylan/asymetric-dual-encoders/m9src/guard9.py:192)).
- The supposedly materialized code hashes are already stale for `eval9.py`, `guard9.py`, `screen.py`, and `teacher9.py`, yet `guard9.py` reports no problems.

So the three 1.5-hour reruns caused by challenger-only changes bought essentially nothing for the anchor. This is the clearest over-engineering failure.

Use dependency-scoped fingerprints:

- One small common protocol fingerprint shared by all arms.
- Per-arm executable/data fingerprints.
- A dependency DAG determining exactly which results a change invalidates.
- Payload hashes stored in the consumed token and recomputed by `eligible()`.

### MAJOR — the allocator setting is not pinned

This line:

```python
os.environ.setdefault("PYTORCH_CUDA_ALLOC_CONF", "expandable_segments:True")
```

does not pin anything ([m9base.py](/home/dylan/asymetric-dual-encoders/m9src/m9base.py:29)). An operator-provided conflicting value wins silently—the exact failure mode already fixed for `M7_ENCODER`.

Reject a conflicting value or assign it unconditionally before importing Torch.

Moving DEV-6 to the final checkpoint does not invalidate the final DEV-6 contrasts. It does, however, weaken the rank-stability rule: adoption is decided on final DEV-6, while “stability” is now measured on SCREEN-3. That no longer tests stability of the decision-surface ranking; it is a proxy veto. Either call it that or remove it.

The adequacy gate is less problematic because it is honestly described as a budget trigger. SCREEN-3 is adequate for that limited purpose.

### MAJOR — the port “gate” is not a gate

Recording fp16 parity as FAIL rather than moving the threshold was exactly right.

But operationally:

- The current port artifact belongs to an older session and `eligible()` returns false.
- The current session has no `m9-port-pilot` token.
- `require_predecessors()` skips every `m9-*` pilot ([screen.py](/home/dylan/asymetric-dual-encoders/m9src/screen.py:82)).
- `port.py` exits successfully even when `pass_all` is false ([port.py](/home/dylan/asymetric-dual-encoders/m9src/port.py:231)).
- The fp16 graph records cosine but not its own max-absolute error, despite the locked two-part parity condition.
- Fastembed registration names `model.onnx`—the 135.6 MB fp32 graph—as the model file, while the 68.5 MB fp16 graph is merely an additional file ([port.py](/home/dylan/asymetric-dual-encoders/m9src/port.py:203)). It does not demonstrate a serving route for the ≤70 MB artifact.

The M10 follow-up is directionally right: preregister a retrieval-impact tolerance before measuring it. It should test the actual fp16 graph through the actual Fastembed serving path, including per-example numerical diagnostics. M9 may continue quality screening, but the current FAIL blocks a portability/ship claim.

## The warm-start selection

It is now free of DEV leakage in the meaningful sense:

- No DEV surface is read.
- Fit and validation rows are disjoint.
- In the actual selected sample, there are zero duplicated text values crossing the split.
- The normalized objective matches training.

However, the split is not randomized as described. The 60,000 sampled indices are sorted, then the first 50,000 fit and last 10,000 validate ([warmfit.py](/home/dylan/asymetric-dual-encoders/m9src/warmfit.py:63)). Consequently:

- Fit indices span 1–202,223.
- Validation indices span 202,230–242,785.
- Fit p95 length is 26 words; validation p95 is 16.

So it is a training-only, leak-free, index-contiguous holdout—not an ordinary random 50K/10K split. That is unlikely to invalidate λ=1e-4, especially given the extremely flat validation values, but it should be corrected or disclosed.

Two smaller issues:

- Selection is performed on objectives rounded to six decimals ([warmfit.py](/home/dylan/asymetric-dual-encoders/m9src/warmfit.py:46)).
- λ is calibrated only in the incumbent-bge feature space and then globally reused. Call it an anchor-calibrated global λ, not “per-arm calibrated.”

## What is over-engineered

Bluntly: the discipline is now eating the experiment.

Not earning its cost:

- The all-or-nothing session fingerprint.
- Re-running deterministic incumbent arms after challenger-only edits.
- A K=2 seed replica explicitly read by no rule.
- SCREEN-3 “rank stability” attached to DEV-6 decisions.
- Repeated provisional `decide()` artifacts masquerading as final decisions.
- Duplicate code hashes in `m9_lock_constants.json` plus a separate live fingerprint.
- An append-only 637-line ledger mirrored into registry, STATUS, RESULTS, comments and CODEMAP. They now contradict each other: `LEDGER.md` §3 says SCREEN-3 adequacy, while §4.4 still says DEV-6 ([LEDGER.md](/home/dylan/asymetric-dual-encoders/m9/LEDGER.md:235), [LEDGER.md](/home/dylan/asymetric-dual-encoders/m9/LEDGER.md:391)).

Earning its cost:

- The corrected training-only warmfit.
- The warm-start ablation: +0.0265 is large and Stage 0 is cheap.
- Anchor-first staging; one curve before five contrasts was the right call.
- Full-row finiteness/unit-norm checks.
- bf16 challenger encoding, once cache invalidation is fixed.
- Materialized token schedules and exhaustion/nonempty-step assertions.
- Pinned qid manifests and fixed contrast orientation.
- Refusing to re-threshold the fp16 parity result.
- Atomic result publication and a run-start state check—implemented more simply and with artifact hashing.

My immediate recommendation: let the current anchor finish, then pause. Fix the challenger cache key/combined-cache bug, separate provisional from final decisions, make the allocator setting real, and have Dylan explicitly ratify or reject the reordered Stage B. Do not pay for another global anchor rerun after those challenger-only repairs.
